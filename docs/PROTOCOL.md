# FileDrop Wire Protocol

All protocol code lives in `rust/filedrop-core/src/{discovery,transfer,pairing,security}/`.
This document describes the bytes on the wire, independent of the Rust
types that implement them.

## 1. Discovery

### 1.1 mDNS / DNS-SD (primary)

Service type: `_filedrop._tcp.local.`

Each device registers a DNS-SD service instance with:
- Instance name: the device's display name (dots replaced with `-`,
  since DNS-SD instance names can't contain them).
- Hostname: `<device-name>.local.`
- Port: the device's HTTP server port (default 53317, see §3).
- TXT records:
  - `device_id` — the device's UUID (v4), used to deduplicate/identify
    across mDNS and UDP-broadcast discovery.
  - `platform` — one of `android`, `ios`, `macos`, `windows`, `linux`.

Browsing devices watch for `_filedrop._tcp.local.` `ServiceResolved`
events and read the above out of the resolved record.

### 1.2 UDP broadcast (fallback)

Used when multicast is blocked on the local network. Port **53318**.

Each device periodically (every 5s) broadcasts a JSON UDP datagram to
`255.255.255.255:53318`:

```json
{
  "magic": "FILEDROP_ANNOUNCE_V1",
  "device_id": "b3f2b1a0-....-....-....-............",
  "name": "Ashvini's MacBook",
  "port": 53317,
  "platform": "macos"
}
```

Receivers listening on `0.0.0.0:53318` validate `magic` before trusting
the packet, and ignore their own `device_id` (self-announcements loop
back on broadcast). The sender's source IP (`recv_from`'s peer address)
is used as the device's address — never a field inside the packet
itself, so a malicious peer can't claim to be reachable at an address it
doesn't control.

## 2. Pairing

Pairing establishes mutual trust between two devices before either will
accept files from the other without a prompt.

### 2.1 Token

A pairing token is 32 cryptographically random bytes, URL-safe base64
(unpadded) encoded — 43 ASCII characters. Generated by
`filedrop-core::pairing::generate_pairing_token`. Tokens are single-use
and time-limited (default TTL: 300s), tracked by
`filedrop-core::pairing::PairingStateMachine`.

### 2.2 QR payload

For in-person pairing, the token is embedded in a QR code encoding this
JSON (`filedrop-core::pairing::QrPairingPayload`):

```json
{
  "version": 1,
  "device_id": "....",
  "device_name": "Ashvini's MacBook",
  "address": "192.168.1.42",
  "port": 53317,
  "token": "base64url-token...",
  "expires_at": 1758150000
}
```

### 2.3 Handshake

1. Device A generates a token, registers a `Pending` pairing request
   keyed by (expected) peer device id, and displays it via QR or shares
   it out-of-band.
2. Device B scans/enters the token and calls Device A's server,
   presenting the token (see §4.2, `X-FileDrop-Pairing-Token` header on
   a future pairing-specific endpoint — reserved for Phase 3).
3. Device A validates the token in constant time
   (`security::tokens_match`) and, if valid and unexpired, moves the
   request to `AwaitingConfirmation` and emits a `PairingRequested`
   event to its own UI.
4. The local user on Device A accepts or rejects. State moves to
   `Paired` or `Rejected` accordingly.
5. Once `Paired`, transfers between the two devices proceed without a
   fresh pairing prompt (persisted pairing state is a `storage`-layer
   concern for a later phase; the state machine here only governs the
   live handshake).

## 3. Server & Port

Default port: **53317**. If unavailable, the server scans upward through
53317–53350 for the first free port (`networking::pick_server_port`).
The bound address/port is what gets advertised via mDNS/UDP broadcast
and embedded in QR payloads.

## 4. Transfer

### 4.1 Endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/transfer/:transfer_id` | Start or resume a transfer. Body = file bytes (or remaining bytes, for a resume). |
| `GET` | `/api/v1/transfer/:transfer_id/status` | Current bytes-received offset + status, for a sender deciding whether/where to resume. |
| `GET` | `/health` | Liveness check (used by the optional nginx config). |

### 4.2 Request headers (`POST /api/v1/transfer/:id`)

| Header | Required | Meaning |
|---|---|---|
| `X-FileDrop-Filename` | yes | Original filename. Sanitized server-side (`security::sanitize_filename`) before any filesystem use — never trusted as-is. |
| `X-FileDrop-Total-Size` | yes | Total file size in bytes, decimal. |
| `X-FileDrop-Sha256` | no | Sender-computed SHA-256 hex digest of the *complete* file, for end-to-end verification on receipt. |
| `Content-Range` | no (yes for resume) | `bytes START-END/TOTAL`. Presence signals "this is a resumed upload starting at byte `START`"; the receiver seeks its `.part` staging file to `START` and appends rather than truncating. |

### 4.3 Chunking

The request body is a raw byte stream, read by the receiver in **1 MiB**
chunks (`transfer::CHUNK_SIZE`) via `axum`'s `Body::into_data_stream()`
and written straight through to a `.part` file on disk — the full file
is never buffered in memory on either side. The sender mirrors this: a
`tokio_util::io::ReaderStream` wraps the source file and feeds
`reqwest::Body::wrap_stream`, so sending is equally streaming.

### 4.4 Responses

| Status | Meaning |
|---|---|
| `200 OK` | Transfer complete and (if a checksum was sent) verified. |
| `206 Partial Content` | Connection dropped mid-upload; the partial `.part` file was kept and the transfer is resumable via `Content-Range` on a subsequent request. |
| `400 Bad Request` | Missing required headers, unsafe filename/path, or a body stream error. |
| `422 Unprocessable Entity` | SHA-256 checksum mismatch — the `.part` file is deleted rather than kept, since silent corruption is worse than forcing a clean retry. |
| `499` (non-standard, used deliberately) | Transfer was cancelled mid-stream by the receiving user; the partial file is deleted. |
| `404 Not Found` | (status endpoint only) unknown `transfer_id`. |

### 4.5 Resume flow

1. A dropped connection leaves a `.part` file on the receiver at
   whatever byte offset it reached.
2. The sender calls `GET /api/v1/transfer/:id/status` to learn how many
   bytes the receiver already has (or, in a simpler client, just retries
   from the last chunk boundary it knows locally).
3. The sender re-issues `POST /api/v1/transfer/:id` with `Content-Range:
   bytes <offset>-<total-1>/<total>` and a body containing only the
   remaining bytes (seeked to `<offset>` in the source file).
4. The receiver seeks its staging file to `<offset>` (without
   truncating) and appends.
5. On completion, since the resuming request's hasher only saw the tail
   of the file, the server re-hashes the **entire** `.part` file from
   disk via `security::sha256_file` before comparing against
   `X-FileDrop-Sha256`, rather than trusting a partial in-memory digest.

### 4.6 SHA-256 verification flow

- **Sender**: hashes the source file before sending (or incrementally
  while sending — see `transfer::client::SendOptions` doc comment for
  why this implementation chooses to hash up-front) and sends the digest
  in `X-FileDrop-Sha256`.
- **Receiver**: hashes bytes as they're written (fresh transfer) or
  re-hashes the completed file from disk (resumed transfer), then
  compares against the header. Mismatch → `422`, `.part` file deleted,
  forcing the sender to retry from scratch rather than risk delivering
  corrupted data.

## 5. Security notes

- **Path traversal**: every filename received over the wire goes through
  `security::sanitize_filename` (strips path separators, `..`,
  control/reserved characters) and every filesystem join goes through
  `security::safe_join`, which lexically rejects any path that would
  resolve outside the intended base directory.
- **Pairing token comparison** is constant-time (`security::tokens_match`)
  to avoid leaking how many leading bytes matched via response timing.
- **No implicit trust**: an unpaired device can initiate the pairing
  handshake, but the receiving device's local user must explicitly
  accept before files are ever written to disk from that peer (Phase 3
  wires this into the transfer-accept flow end-to-end; the state machine
  itself is complete now).
